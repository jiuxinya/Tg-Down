# v3.2 开发规划

> 状态：2026-08-24 实施完成，全部条目已落地，除下方"执行期调整"列出的三项。

范围（2026-08-24 确认）：**功能性收敛版本**——不加新功能。内容为四类：
v3.0/v3.1 交付审计挖出的缺陷修复、v3 规划（docs/v3-plan.md）未完成项全部收口、
桌面端（v3.1）毛边打磨、测试与发布质量基线补齐。

边界：分发面只修复现有产物，不扩 darwin-amd64 / linux-arm64；
真实账号集成测试补齐 8 场景并接 nightly CI（需用户提供测试账号 secrets）。

交付方式：一次性发布 v3.2.0。v3.1.0 之后已合入未发布的 4 个提交
（队列落盘串行化、TDLib 取消等待、lint 清零、依赖升级）随本版本发出。

## 执行期调整（相对本文原定范围）

实施中查实了三处，据此调整：

1. **nightly 集成 CI 不做**：需要仓库配置真实账号 secrets，非本轮可完成。
   6 个集成场景已补齐（`internal/telegram/integration_scenarios_test.go`），
   仅通过编译与 lint 验证，**尚未对真实账号跑过**；接 CI 待 secrets 就位。
2. **多类型任务的 ScanCursor 标志不做**：核对后发现前端从未渲染 `scan_cursor`，
   且该字段是 `omitempty`，值为 0 时根本不出现在 JSON 里。加一个"不可断点续扫"
   标志等于加一个无人消费的字段。原判断"DTO 把恒 0 的游标发给 UI"不成立。
3. **GetMe 失败告警不做**：该失败已按 WARN 级进日志，而 v3.1 的日志页支持按级别
   筛选与错误/警告快捷视图，用户可见。要做成 `/api/state` 告警需新增
   `tgapi.Client` 接口方法 + 状态字段 + 前端渲染，为一个已可见的次要问题引入
   一条通用告警通道，收益不足。

另有一项原判断有误但已按新理由处理：`auto-release.yml` 被描述为"死代码"，
实际它仍可经 `workflow_dispatch` 手动触发并正常工作，只是与"发布统一由人工打 tag"
的既定策略重复。**本轮未删除**——删除工作中的功能不应基于一个错误前提。

明确不做（v3 规划遗留项中主动放弃的）：

- per-file 重试端点：现有 `POST /api/tasks/{id}/retry` 已改为原地补失败文件，粒度需求已消失
- 去重复制 reflink/clonefile：hardlink + copy 回退已够，收益不抵平台分支复杂度
- 邀请链接（t.me/+xxx）支持：属新功能，推 3.x

## M1 核心引擎正确性

审计确认的行为缺陷，多数用户可见。

- [x] **默认类型集剔除 sticker**（`internal/media/media.go:34`）：DefaultTypes == AllTypes 含 sticker →
      未设过滤器的任务全部退化为 SearchMessagesFilterEmpty 全量翻页（`internal/telegram/client.go:1911-1918`），

      前端注释（`web/src/format.ts:12-13`）已按"默认不含 sticker"书写，与实现矛盾——按注释方向修
- [x] **限频不再产出偏小 expected_total**（`client.go:1729-1748`）：单过滤器 FLOOD_WAIT 走 `continue`
      仍返回成功 → 进度条超 100%。GetChatMessageCount 补 retrier（v3 规划 M1 遗留的最后一个裸调），
      仍失败时按"总数未知"处理而非偏小值
- [x] **去重复制文件补写 sidecar**（`internal/downloader/downloader.go:873` vs `:1037-1043`）：
      writeMetadataSidecar 只在 completed 路径执行，copyFromDuplicate 落盘的文件无 .json
- [x] **历史分页排序加 tiebreaker**（`internal/store/history.go:283`）：ORDER BY created_at DESC
      无次键，同秒批量入库的行跨页可重复/丢失（与 M3 keyset 同一改动面）
- [ ] 多类型任务 ScanCursor 恒 0（`internal/telegram/scan.go:186-193`）：多 pipeline 不追踪游标是
      已接受的取舍，但 TaskDTO 仍把 0 值游标发给 UI——DTO 隐藏或标注"不可断点续扫"
- [ ] GetMe 失败收藏夹静默消失（`client.go:987`）：告警进 `/api/state`，UI 可见
- [x] 任务级速度与 ETA（v3 规划 M1-11 尾巴）：per-file 已有（`downloader.go:390-408`），
      TaskDTO（`internal/queue/queue.go:70-99`）无 speed/eta 字段，聚合后补进
- [x] schema_version 表补 UNIQUE + upsert（`internal/store/store.go:104-106,290-294` 现纯 INSERT 靠 MAX 读）；
      dropObsoleteIndexes（`store.go:191-194`）纳入版本门，消除每次启动的无条件 DDL

## 顺序与依赖

**M1 + M3 → M4；M2、M5 独立并行；M6 贯穿**

- M1 与 M3 同动 store/history，连着做避免二次进场；keyset 与排序 tiebreaker 是同一改动
- M4 的历史排序/导出/任务详情依赖 M3 定稿分页与过滤接口
- M5 独立且影响现有用户（产物缺件），最先做
- M6 的 lint/CI 强化先行；nightly 集成最后接（依赖场景补齐与 secrets 就位）

## 破坏性变更

- SQLite schema 升级 v4（FTS5 表 + schema_version 约束），自动迁移，不支持回退
- 历史列表 API 分页语义变化（keyset cursor 替代 page/page_size），前后端同步改造
- nightly 集成 CI 需要仓库配置测试账号 secrets（TG_TEST_API_ID / TG_TEST_API_HASH / 会话材料）
